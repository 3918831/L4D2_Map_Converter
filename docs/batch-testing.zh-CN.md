# 批量地图预检查、构建与采样

`batch-check` 逐项调用现有单图 `check`，生成 JSON 证据和 Markdown 汇总。它只读取输入、制定并审计内存中的转换方案，不写 BSP/VPK、不运行原生工具、不启动游戏。报告写入单独的新目录。通过不代表可以编译、全部素材可用、效果正确或玩法已验收。

## 准备任务清单

先按 [通用转换指南](generic-conversion.zh-CN.md) 为每个“来源地图 + 目标预设 + 规则版本”准备一份完整配置。不要把已接受旧运行的 output_dir 当作新构建目标；每项配置使用独立目录。C5M1 与 C4M3 可混在同一批中，规则版本也逐项明确，不自动升级旧配置。

将 `examples/batch.example.json` 复制到自己的目录并修改：

```json
{
  "schema_version": 1,
  "jobs": [
    {"id": "c1m1-c5m1", "config": "./configs/c1m1-c5m1.local.json"},
    {"id": "c6m1-c5m1-v2", "config": "./configs/c6m1-c5m1-v2.local.json"}
  ]
}
```

这些 config 路径是待创建的本地配置，不是示例附带的游戏路径。任务 ID 必须唯一，只能用小写字母、数字、下划线和连字符，长度 1–64。清单仅接受示例中的键；`config` 相对清单解析，而配置内部的路径仍相对各自配置文件解析。重复 JSON 键拒绝。配置文件缺失或内容无效属于该项失败，其余项继续。

批量报告目录不得位于游戏/工具安装内，也不能与任何配置的未来 output_dir 相同或互相包含。任务 output_dir 不能重复或嵌套；路径冲突和清单结构错误在写报告前拒绝，修正后重新执行。

## 执行

```powershell
python -m l4d2_bsp.workflow batch-check --manifest batch.local.json --output artifacts/batch-check-01
```

退出码 0 表示全部任务通过本次预检查；2 表示至少一项失败，或清单/报告写入失败。以控制台错误和报告区分两种情况。每次使用不存在的新报告目录；不会覆盖、自动重试或续跑已有批次。当前顺序执行，避免同时读取多个大 BSP 占用过多内存。

报告内容：

- `manifest.json`：原清单字节快照。
- `summary.json`：任务状态、通过/失败/未完成数量、清单哈希、程序模块哈希与版本。
- `summary.md`：可阅读的检查结果和警告数量。
- `jobs/<id>.json`：配置快照与哈希、完整单图预检查方案、检查前后输入清单、警告；失败时记录阶段、异常类型与原文，并保留已取得的证据。配置验证失败也尽力记录显式声明的可读输入身份，不用取证失败覆盖原错误。

警告可与 passed 同时存在。资源检查只沿用单图 check 的目标预设资源范围，并非整张地图的完整依赖闭包。脚本、运行时目标、模型/烘焙兼容性和视觉缺口仍须看详细报告及后续阶段。

失败按发生阶段归类，不根据错误文本猜测根因：

| 分类 | 含义 |
|---|---|
| `missing_file` | 文件访问报告文件不存在；阶段字段指出发生位置 |
| `configuration_and_inputs` | 配置、伴随文件发现、NAV、安装或工具路径检查失败 |
| `input_format` | 基础 BSP 读取/结构检查失败 |
| `conversion_rejected` | 基础图或模式补丁的格式、修改方案、实体/IO 保护检查拒绝 |
| `resource_check` | 目标风格资源查找或完整性检查失败 |
| `input_identity` | 预检查与归档之间发现输入/配置/预设变化 |
| `internal_error` | 未预期程序异常，保留 traceback；不能当作“该地图不支持” |

每完成一项便保存结果；Ctrl+C 时记录当前项 interrupted，后续项 pending。强制结束进程时最后状态可能是 running；这不表示通过。报告写入失败会终止批次，不伪造完整报告。重新运行选择新的报告目录。

## 串行构建与自动采样

`batch-run` 使用同样的任务清单，先重新预检查整批，再逐项调用现有单图 build 和 auto-capture。请先按 [自动采样指南](auto-capture.zh-CN.md) 验证启动配置；批次中所有任务必须匹配这份启动配置的游戏安装，且使用 `replace` 策略。旧 `preserve` 路径不会自动改为 replace。

```powershell
python -m l4d2_bsp.workflow batch-run --manifest batch.local.json --output artifacts/batch-run-01 --launcher launcher.local.json
```

执行前完全退出游戏；等待期间不要手动启动游戏、加载其他地图、修改配置/输入或执行采样命令。游戏会随任务逐次启动、采样、退出。报告目录和每项 output_dir 必须是新的，预检查报告不能用作 batch-run 输出目录。不会自动复用之前的构建、采样或验收。

- 基础配置/输入/修改方案不支持的任务记录失败，其他任务继续。某份配置已有 output_dir 也会跳过并保留原目录。
- 离线构建/审计预期失败记录到该任务后继续；内部程序异常停止执行队列。
- 采样、退出、清理、最终哈希检查或共享环境检查失败时，批次为 `blocked`，后续保持 `pending`。即使单图失败处理已清理成功，首版也保守停队列，方便检查现场。
- 同一安装使用批次锁，自动采样继续使用原有游戏锁与进程检查。不要同时运行手动单图流程；该锁不是对所有外部程序的排他控制。
- 不强制杀进程，不删除无关插件，不自动重试、不自动续跑。Ctrl+C 保留 interrupted；强制退出可能留下 running，不能当作完成。

报告目录包括 `preflight/` 完整预检查证据、`jobs/<id>.json` 阶段记录、`jobs/<id>.log` 单图构建/采样输出、`summary.json/md` 汇总，以及 `acceptance.json` 待人工验收清单。完整烘焙/采样审计和恢复收据仍位于各自 output_dir；报告不取代单图运行目录。清单中的最终包绑定 run_id、文件路径及 SHA256。`ready` 仅表示离线构建、自动采样、打包与清理通过；最终包未自动安装，human_acceptance 始终为 not_run。

若 blocked，先查看失败项 stage/error 和单图 `auto-capture/attempt.json`。后者存在且需要恢复时，完全退出游戏后执行：

```powershell
python -m l4d2_bsp.workflow recover-auto-capture --run "该项的 output_dir"
```

该命令只恢复启动器和有收据的临时文件，不重采样。若没有 attempt.json，按记录的环境/构建错误处理。修正后建立新的清单，仅列待重试任务，并为它们指定全新的 output_dir 和批量报告目录；已成功的任务不用重做。退出码 0 只表示整批 ready，其他结果为非零；以持久化报告确认具体状态。

## 人工验收与后续迭代

按单图指南将一个最终 VPK 安装到 addons。相同原地图的旧风格包需先停用，保留备份；批量工具不会处理这些最终部署冲突。通过原地图名加载，逐图记录“接受”“带已知限制接受”“不接受”“未测试”，关联 run_id、最终包哈希、截图和实际观察路线。可将人工记录保存在各运行的 `manual-validation/`，不要修改机器阶段冒充人工结论。批量 acceptance.json 是机器生成的待办清单，不是人工结果录入接口。

已有验收不自动继承给新产物；C6 白椅 VIS-001 仍保留。后续再增加按收据恢复、验收录入和更大批次，不以跳过保护检查扩大覆盖。

三方图也使用相同清单和单图配置，需先提供松散 BSP、NAV、模式补丁和所需资源。先记录缺口，再通过可复用规则迭代，不按地图名绕过检查。当前未执行三方图批量验收。
